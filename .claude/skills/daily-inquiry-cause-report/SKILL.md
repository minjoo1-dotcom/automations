# 전일자 한도조회 원인추적 스레드 초안 작성

전일자 "조회 유저수"의 **전주 동요일 대비** 증감을 매체구분→매체별로 분해하고, 일회성 발송 특이사항을 결합해 **원인추적 본문 초안**을 만든다(완성분은 채팅 출력이 기본, 요청 시 **사용자 본인 DM으로 전송** — #growth 부모 스레드엔 넣지 않음). 시트의 증감 계산·공유문 생성은 이미 자동이므로 이 스킬은 **원인추적 서술만** 담당한다.

## 시작 동작 (호출 즉시)
스킬이 호출되면 아래 체크리스트를 띄우고 자료를 기다린다. **매체 성과의 1차 소스 = 사용자 대시보드 캡쳐(입력 B)** 이다(입력 A의 Databricks PDF 자동파싱은 2026-08-11 숫자 불일치로 보류 — 아래 입력 A 경고 참조). 이미 캡쳐/자료가 함께 왔으면 바로 절차로 진행.

> **전일자 한도조회 원인추적 초안을 만들게요. 아래를 주세요:**
> 1. 📸 태블로 **매체구분별 전체 성과(D0)** 캡쳐 (전일 + 전주 동요일; "최근 8주 같은 요일" 필터면 그대로)
> 2. 📸 태블로 **매체별 전체 성과(D0)** 캡쳐 (전일 + 전주 동요일)
> 3. 🔢 **전사 조회 유저수** 헤드라인 — 전일·전주동요일 값 또는 증감(%) *(캡쳐엔 없음. "타앱한도조회 알림톡" 시트/9시 메일. 항상 필요)*
> 4. 📝 금주 **발송상세(전일 CRM 성과) 캡쳐**(유입수용) — 캠페인 **유입수(명)=`D0 오픈-한도조회 유저수`** 채우는 용. 없으면 금주는 발송수(만)로 표기. 캠페인명은 #growth_internal "[M/D CRM 모니터링]" 스레드서 자동, 전주 캠페인은 #growth 전주 성과 스레드서 자동.
> 5. 🔗 *(선택)* 스레드에 넣을 거면 부모(= #growth "📊 N월 누적 MS (M/D 기준)" 봇 글) Slack 링크
>
> *🗓️ **월요일 보고**(전일=금+주말)면 금·토·일 3일치 캡쳐를 주세요.*

## 입력 A — Databricks 구독 PDF 자동 파싱 (⚠️ 2026-08-11 보류 — 대시보드와 숫자 불일치)
> ⚠️ **보류**: 메일 PDF 숫자가 팀 표준 태블로 대시보드와 계통적으로 10~20% 다름(8/10 CRM 8,428 vs 7,156 등, 필터 정의 차이 추정). **당분간 입력 B(사용자 대시보드 캡쳐)를 1차로 쓴다.** 아래 파싱 로직은 불일치 규명 후 재개용으로 보존. 시작 시 PDF가 있어도 곧바로 신뢰하지 말고, 사용자에게 대시보드 캡쳐 제공을 우선 요청한다.

Databricks가 매일 새벽(~01:36) `noreply@databricks.com`으로 **"Dashboard snapshot: CRM Daily 성과 모니터링 - 마케팅_Daily_특화"** 메일을 보낸다. 첨부 PDF에 매체구분별·매체별 D0 한도조회 유저수가 **16일치**(전일~16일 전, 최신순) 들어있어 태블로 캡쳐 2장을 대체한다. ⚠️ **Gmail MCP는 첨부를 못 가져오므로**, Apps Script(`apps_script_save_databricks_pdf.gs`)가 PDF를 Drive 폴더 `Databricks_CRM_Daily_snapshots`에 자동저장 → 스킬은 **Drive에서 읽는다**.

**PDF 찾기 & 파일 선택**: Drive `search_files` →
`title contains 'CRM Daily 성과 모니터링 - 마케팅_Daily_특화' and mimeType = 'application/pdf'`
→ ⚠️ **하루에 스냅샷이 2개** 온다: `[Public]...-YYYYMMDD_23-26.pdf`(전날 밤, 최신행=그날 D0)와 `...-YYYYMMDD_01-36.pdf`(다음날 새벽, 최신행=전일 D-1). **파일명 날짜는 생성시각일 뿐 데이터 기준일이 아니다** → 파일명으로 고르지 말 것. 대신 **후보들을 read_file_content로 읽어 날짜행(첫 줄 date 리스트)의 맨 앞=그룹0 날짜를 확인**하고, **그룹0 == 전일(=보고일−1)인 파일**을 고른다. 두 버전 다 그룹0=전일이면(예: 화요일 아침엔 월요일밤 [Public]과 화요일새벽 regular 둘 다 그룹0=전일) **최신 생성분(가장 정산된 값) 우선**. 두 버전 숫자는 ±1~3 차이(5~10명 반올림 후 동일).

**추출 텍스트 구조** (검증 2026-08-10):
- **① 매체구분별 (D0)**: 숫자 스트림이 **6개씩 = `[CRM, DA(RE), DA(UA), Organic, Other, SA]`**, 한 그룹 = 하루, **최신순**(그룹0 = 전일). 16그룹. 컬럼 고정이라 위치 파싱이 안전.
- **② (CRM Only) 매체별 (D0)**: 하루당 `[ka-alimtalk, ka-brand, ka-brand-txt, ka-friend, ka-menu, (lms), push]`. **lms는 0이면 생략**되어 하루 6개 또는 7개로 가변. 위치 규칙: 값 6개면 `[ka-alim, ka-brand, ka-brand-txt, ka-friend, ka-menu, push]`(lms=0), 7개면 push 앞에 lms 삽입.
- **③ 타사한도조회 블록**(보너스): `전일 타사한도조회자 / 동요일 타사한도조회자 / 동요일 대비 증감율(%)` — plan_id=6130 알림 기준(전사 dedup 헤드라인 아님, 참고용).

**★필수 checksum**: 각 날짜에 대해 **②의 매체별 합 == ①의 CRM 값**이어야 한다(예: 8/09 = 411+10+3+39+1+329 = 793 = CRM). 날짜별로 이 등식을 **반드시 대조**한다.
- 전부 일치 → 파싱 신뢰, 진행.
- 어느 날짜라도 불일치 → 위치 파싱이 깨진 것. 추측 금지. **PNG 폴백**: 같은 메일의 `...-desktop.png` 첨부(Drive에 있으면)를 `download_file_content`로 받아 로컬 저장 후 이미지로 판독하거나, 사용자에게 해당 날짜 캡쳐를 요청.

**날짜 선택**: 그룹0 = 전일. 전주 동요일 = 그룹0에서 7 뒤(그룹7). 월요일 변형은 금(그룹2)·토(그룹1)·일(그룹0)과 각 +7(전주). PDF 한 장으로 전부 커버되므로 캡쳐 여러 장 불필요.

## 입력 B — 태블로 캡쳐 (폴백, PDF 자동파싱 실패 시)
1. **태블로 "매체구분별 전체 성과(D0)" 캡쳐** — 컬럼: date, CRM, DA(RE), DA(UA), Organic, OtherM.., SA, 총합계. 전일 행 + 전주 동요일 행(동일요일 필터) 포함.
2. **태블로 "매체별 전체 성과(D0)" 캡쳐** — 컬럼: date, ka-alim(카카오 알림톡), ka-brand, ka-bran..(카카오 브랜드=ka-brand-txt), ka-friend, ka-menu(메뉴), lms, push. 전일 + 전주 동요일 포함.
3. **헤드라인 전사 조회 유저수** — 전일 & 전주 동요일 값(또는 이미 계산된 증감·%). ★캡쳐(매체표)에 **없음**. 전사 기본수치 대시보드/9시 전사수치 메일에서 옴. 매체 총합계로 대체하지 말 것(유니크 dedup이라 다름).
4. **캠페인 귀속 소스 (전주+금주 발송내역)** — 월별 CRM 문서 "26.MM CRM"(예: https://findainc.atlassian.net/wiki/spaces/MD/pages/5442241108/26.08+CRM)의 해당 일자 발송내역, 또는 발송툴 상세 표. ★Confluence는 **IP 제한(망분리)으로 직접 fetch 불가** → 사용자가 해당 부분을 텍스트로 붙이거나 이미지로 제공해야 함. 여기서 push·ka-bran(브랜드)·lms 주요 캠페인 + 한도조회 유입수(`DO 한도조회 유저수`)를 뽑아 **금주** 라인을 채운다(정식명 모르면 광고식별자+planID). 평일/휴일 split은 사용자 확인. **전주 라인은 #growth의 전주 동요일 성과 스레드(reply)에서 직접 읽어온다**(별도 발송내역 없이도 가능 — `slack_read_thread`). 내용이 없으면 매체 단위까지만 쓰고 부족분을 물어본다.

## 절차
1. **판독**: 매체구분/매체별 전일·전주 동요일 값을 확보한다. **기본은 입력 A(Drive의 Databricks PDF 파싱)** — checksum(②합=①CRM) 통과 후 그룹0/그룹7(월요일은 그룹2·1·0 및 +7)에서 값을 뽑는다. PDF 없으면 입력 B의 두 캡쳐에서 전일·전주 동요일 행을 읽는다.
2. **매핑 & 증감 계산** (전일 − 전주 동요일):
   - **CRM**(매체구분) 총 증감. 하위 분해 = push · ka-alim(알림톡) · ka-menu(메뉴) · ka-bran(브랜드) [매체 표]. 하위 합 ≈ CRM 총과 맞는지 확인.
   - **PAID**: SA + **DA(=DA(RE)+DA(UA))**.
   - **ORGANIC**: Organic.
   - 소액(OtherM.., ka-friend, lms, ka-brand=0, ka-menu 미미)은 생략(±50명 미만).
   - 헤드라인 증감(명·%)은 **입력받은 전사 조회 유저수**로 계산. 매체 합과 다를 수 있음(정상 — dedup).
3. **숫자 에코 → 확인**: 서술 전 위 값을 표로 제시하고 사용자 확인(PDF는 checksum 결과도 함께 표시, 캡쳐는 OCR 오독 방지). 확정 후 서술.
4. **정합 참고**: CRM 하위합 vs CRM 총, 매체구분 총합계 증감을 표시하되, 헤드라인은 별도 전사 수치임을 명확히.
5. **원인 서술**: 증감폭 ±50~100명 이상 매체(push·lms·브랜드 등)에 원인. 헤드라인 바로 아래 **요약 한 줄**(가장 큰 기여 매체구분+요인).
   - **전주 캠페인**: #growth의 **전주 동요일 성과 스레드(reply)**에서 정식 캠페인명·유입수를 가져온다(예: 7/29 스레드에서 '새로운 대출 소식 컴 푸시 1,165명'). 사용자가 스레드 링크를 주거나, 없으면 `slack_search`/`slack_read_thread`로 찾는다.
   - **금주 캠페인**: 유입수는 발송상세의 `DO 한도조회 유저수` 기준(마수동 등 변형 합산). **정식 캠페인명 매칭은 `af_ad`(광고식별자) 우선** (2026-08-13 확정): 발송상세의 af_ad(예: `lacondition`·`laintro-deni`·`findapost`)로 캠페인 정체성을 잡는다 — 같은 af_ad는 주차가 달라도 동일 캠페인이므로 **전주 라인 명칭과 자동으로 일치**한다(af_ad→정식명 예: `lacondition`=신용점수대별 조건 푸시, `laintro-deni`=올거절 재터치 푸시, `findapost`=핀다포스트 정보성 컴 푸시/LMS·주차별 콘텐츠명은 채널로 구분). **발송수(만 단위) 매칭은 폴백**(af_ad로 특정 안 될 때만) — 발송수는 모니터링과 어긋나는 경우가 있으니 신뢰 후순위. 채널이 겹치는 af_ad(findapost push vs lms)는 채널로 분리. **정식 콘텐츠명은 #growth_internal(`C071PE9G2EQ`)의 당일 "[M/D CRM 모니터링]" 스레드(reply)에서 확인**하되, af_ad로 잡은 정체성과 대조해 확정. 모니터링 스레드가 없으면 광고식별자(af_ad)+planID로 표기하고 사용자가 교체.
   - **★공휴일 요일 이동 보정** (2026-08-19 확정): 정기 캠페인(예: 매주 월요일 타사 한도조회 브랜드메시지)이 **공휴일/대체휴일로 원래 발송요일에서 밀려 다른 요일에 나간 경우**, 전주 동요일 대비(WoW)가 착시로 부풀거나 꺼진다. 이땐 ① **본문은 평소대로 전주 동요일 대비**로 쓰되 해당 매체 증감이 **요일 이동 효과임을 요약·주석에 명시**하고, ② **원래 발송요일의 전주 값과 보정 비교**를 매체구분 레벨(CRM·DA·SA·ORGANIC 총합계)로 간단히 하단 `※ 참고` 블록(이탤릭)에 붙인다. 캠페인 유입수도 원래요일 전주분과 대조(예: 타사 브랜드메시지 8/10월 1,587명 → 8/18화 1,357명 = 유사~소폭 감소). 보정치용 매체구분 캡쳐(해당 요일 필터)는 사용자에게 요청. 예: 8/18(화) 리포트에서 브랜드메시지가 광복절 대체휴일로 월→화 이동 → 전주 화 대비 +1,446 착시, 전주 월(8/10) 대비 보정 시 CRM +150 수준.
   - **★전주 동요일이 공휴일인 경우 전전주 보정** (2026-08-26 확정): **전주 동요일(=WoW 비교 기준일) 자체가 공휴일/대체휴일**이면 그날 트래픽이 급감(또는 급증)해 WoW 전체가 무의미해진다. 이땐 ① **본문 헤드라인·매체구분은 평소대로 전주 동요일 대비**로 쓰되 요약·주석에 **비교 기준일이 공휴일이라 WoW가 기저효과임을 명시**하고, ② **전전주 정상 동요일 대비 보정**을 매체구분 레벨(CRM·DA·SA·ORGANIC·총합계)로 하단 `※ 참고` 이탤릭 블록에 붙인다(주요 정기 캠페인 유입수도 전전주 정상일과 대조). 보정용 매체구분 캡쳐(해당 요일 필터)는 사용자에게 요청. 예: 8/24(월) 리포트 — 전주 8/17이 광복절 대체휴일 → WoW +131% 착시, 전전주 정상 월(8/10) 대비 보정 시 총 −1,171. ## 출력 형식 (Slack 마크다운 — 실제 답글 기준)
강조 서식이 핵심. MCP는 표준 마크다운 `**볼드**` · `_이탤릭_` · `` `code` `` · 중첩 리스트를 Slack 서식으로 변환한다.
- **헤드라인(첫 줄)**: 볼드 `**[M/D (요일) 조회 유저수 X.XX% (N명) 증감]**`
- **요약(둘째 줄)**: 헤드라인 바로 아래 **이탤릭 한 줄**. 가장 큰 기여 매체구분 + 주요 매체 요인 1~2개를 한 문장으로. 예: `_ORGANIC 감소가 전체의 약 절반(−1,580), CRM 감소는 컴 푸시 유입 감소·lms 성과 저조가 두드러짐._`
- **매체구분 레벨 증감(CRM 총 / PAID의 SA·DA / ORGANIC) → 인라인 코드(백틱)**: `1,740명 감소` 등. PAID는 총계 없이 SA·DA 각각.
- **하위 매체 증감(push/알림톡/메뉴/브랜드/lms) → 볼드**: `**665명 감소**` 등.
- **캠페인 유입수·평일/휴일 → 볼드** (캠페인명·"유입"은 일반).
- **금주 캠페인 라인**: **af_ad(광고식별자) 우선 매칭**으로 정식 캠페인명을 붙인다(발송수 매칭은 폴백) — 같은 af_ad는 전주 라인과 동일명이 되어야 정상. af_ad로도 정식명이 특정 안 되면 **광고식별자(af_ad) + planID**로 표기 → 사용자가 Slack에서 교체. 예(확정 시): `신용점수대별 조건 푸시 **403명** 유입` / 예(미상 시): `lacondition (plan 8297·8296) **432명** 유입`. 전주 라인은 전주 동요일 성과 스레드에서 정식 캠페인명을 가져온다.
- 본문 = 중첩 리스트(`-`). CRM 하위 매체는 CRM 아래로 들여쓰고, 캠페인 귀속은 전주/금주를 그 아래 하위 bullet로.
- 구분 하이픈 `-`는 앞뒤로 띄어쓴다 (`매체 - 수치`).
- 매체구분 블록(1/2/3) 사이에 빈 줄 하나씩(번호 1·2·3 유지).
- 증감: 증가/감소 명시, 5~10명 단위 반올림. 에코 단계에선 정확값.
- 순서: CRM → PAID → ORGANIC. 캠페인 라인은 증감폭 큰 매체(push/lms/브랜드 등)에만.
- **★유입 100명↑ 캠페인은 전부 기재** (2026-09-03 확정, 사용자 강조): 전주 대비 변동이 작더라도(=매체 총증감이 "전주와 유사"여도) **한도조회 유입 100명을 넘는 캠페인은 전주·금주 양쪽 모두 발송상세(`D0 한도조회 유저수`) 기준으로 캠페인명+유입수를 빠짐없이 나열**한다. "전주와 유사"·"7명 감소" 식으로 뭉개고 캠페인을 생략하지 말 것 — 다음 주 리포트의 전주 라인 소스가 되므로 누락하면 연쇄로 구멍난다. 전주 라인 유입수를 모르면 추측하지 말고 그 요일 발송상세를 요청해 채운다.
- **CRM 하위 소액 매체(메뉴·알림톡 등)는 각각 별도 줄**로 쓴다(`/`로 한 줄에 묶지 말 것). 예: `- 카카오 메뉴 - **295명 감소**` / 다음 줄 `- 알림톡 - **220명 감소**`. (사용자 선호, 2026-08-26)
- **요일이동/미발송 케이스 금주 라인은 간결하게** (2026-08-26): 정기 캠페인이 요일이동으로 이번 주 해당 요일에 안 나갔으면 금주 하위는 캠페인 나열 대신 `브랜드메시지 미발송`(또는 `해당 발송 없음`)처럼 한 줄로. 전주 라인엔 그날 유입수·요일이동 사유를 적는다.

## 월요일 변형 (주말 성과 첨부)
월요일 보고는 **전 영업일 = 금요일**을 헤드라인·풀 원인추적으로 다루고, 그 앞에 **토·일 간략 성과 블록**을 얹는다(사용자가 금·토·일 3일치 캡쳐를 줌). 실제 스레드 구조:
- **맨 위: 주말 블록** — 토/일 각각 한 줄, **매체구분 레벨만** 나열하고 하위 매체·캠페인은 쓰지 않는다. 순서·표기: `CRM · DA · SA · ORGANIC` **평면 나열**(PAID로 합치지 않고 DA·SA 분리). 증감 숫자는 **볼드**, 5~10명 반올림. 미미하면 `전주와 유사`.
- **구분선**: 주말 블록과 금요일 본문 사이에 `==` 한 줄.
- **아래: 금요일 풀 원인추적** — 평소 형식(헤드라인 볼드줄 + 이탤릭 요약 + 1/2/3 매체구분 분해) 그대로.
- 각 주말일 증감도 전주 동요일(전주 토→금주 토) 대비. 캡쳐에서 토·일 행과 전주 토·일 행을 읽어 계산.

## 게시 (Slack MCP — 본인 DM 전송)
기본은 채팅 텍스트 출력이다. 사용자가 "DM 보내줘 / 전송해줘 / Slack에 넣어줘"라고 요청하면 아래대로 **본인 DM으로 전송**한다. 이 MCP는 표준 마크다운(중첩 리스트, `_이탤릭_`, `` `code` ``, `**bold**`)을 Slack 서식으로 변환한다.
- **대상 = 실행자 본인 DM (하드코딩 금지)**: `slack_send_message`의 `channel_id`에 **스킬을 실행하는 사람(=현재 로그인 사용자) 본인의 user_id**를 넣어 **본인 DM으로 전송**한다. ★특정 user_id를 박아두지 말 것 — 팀원이 써도 각자 자기 DM으로 가야 한다. 본인 user_id 확인 순서: ① Slack MCP가 알려주는 "현재 로그인 사용자 user_id"를 그대로 사용(대개 도구 설명/컨텍스트에 노출됨), ② 모르면 `slack_search_users`로 실행자 이메일(예: 세션 컨텍스트의 userEmail)을 조회해 얻는다. ★#growth 부모 스레드에는 넣지 않는다(각자 DM에서 확인 후 직접 #growth에 올림). #growth MS 봇 글을 부모로 찾거나 `thread_ts`를 계산할 필요 없음.
- **전송 전 반드시 채팅에 초안 노출**한다. 단 사용자가 이미 "DM 보내줘/전송해줘"라고 요청한 경우 그 요청이 승인이므로 초안 노출 직후 바로 DM 전송. 별도 요청 없이 스킬만 돌린 경우엔 초안만 보여주고 전송 여부를 묻는다.
- **경로**: 본인 DM 전송은 `slack_send_message`(channel_id=위에서 확인한 실행자 본인 user_id)를 쓴다. DM은 본인에게만 가므로 즉시 전송해도 무방(사용자 대신 외부 발송이 아님). 전송 후 메시지 링크를 사용자에게 준다.
- 게시 본문은 표준 마크다운으로 작성(위 예시 그대로). 그래프·전사수치 이미지는 사람이 첨부.
- ⚠️ **불릿 렌더**: `slack_send_message`(전송) 경로는 Slack 서버가 마크다운 중첩 리스트를 네이티브 `rich_text`로 변환해 리치로 렌더된다(DM 전송도 동일). 마크다운 원문을 작성창에 붙여넣는 건 블록 서식이 안 걸리므로 권하지 않는다.
